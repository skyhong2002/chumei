# Extraction recovery and observation times

`extract_events.py` now retries due transient failures during an ordinary pipeline run. Each item gets at most four provider requests, including its initial request and requests across prompt changes. A legacy error with no attempt count consumes one attempt. No request contains an internal transport retry or immediate JSON-repair request. Successful activities and confirmed empty/non-event results remain cached for their prompt version. Failed prompt upgrades retain historical events and recurring sessions.

Immediately before provider admission, the extractor reloads the item under its cache lock and atomically saves an incremented attempt with `in_progress: true`. A failed reservation write prevents the request. The pending record preserves historical events, recurring sessions and discovery time. Completion keeps the reserved count, clears the pending/error fields on success and never charges twice. Process death or a failed completion save leaves the reservation charged, with a conservative 24-hour item cooldown. Later runs can retry it within the remaining budget; prompt changes and `--retry-errors` cannot reset that count. An interruption after reservation but before the actual HTTP call also consumes the ambiguous slot.

Timeouts, connections, unavailable gateways, rate limits, quota errors and malformed responses are transient. Authentication, invalid requests and unknown failures wait for explicit `--retry-errors`; that flag still honors cooldowns and the four-attempt ceiling. Prompt changes do not reset an error budget. Retry intervals start at 15 minutes, then one hour, four hours and sixteen hours, capped at 24 hours. Rate limits wait at least 30 minutes; quota/authentication failures wait at least 24 hours. A usable upstream `Retry-After` can lengthen the delay (malformed/nonfinite values are ignored, and extreme values are capped at one year).

The existing `llm_gateway.py` loses the response body and headers when its last 429 fails. This patch leaves that module unchanged and conservatively treats its opaque `gateway unavailable … HTTP 429` exception as a quota failure with a 24-hour cooldown. Genuine HTTP exceptions retaining a response can distinguish rate limits, quota errors and `Retry-After`. Preserving those details in the gateway is a follow-up integration improvement.

Provider-wide transport, service, authentication and quota failures persist a circuit cooldown in `state/extraction_gateway.json`, outside the extraction source-cache directory. The extractor rereads it before each dispatch. Extraction and submission review also check it after image/page/schema preparation, immediately before provider entry, using the same short OS lock as circuit publication. Requests admitted before publication may finish; subsequent admissions defer without spending an attempt. Each extractor can have at most `--workers` requests admitted at once; overlapping submission review may also have an admitted request. Observed global failures are published before saving extraction results, so a completion-save failure cannot hide the cooldown. Submission reviews use one transport attempt. A later pipeline run can build existing cached data during a cooldown. A cooldown is not evidence that ingestion or extraction completed successfully.

Typed JSON decoding and response-shape errors are classified before HTTP text matching. A parser's `column 401` or `char 429` stays an item-local malformed-response error. Legacy opaque HTTP exceptions still recognize explicit `HTTP 429` and `400: ...` forms.

Extraction holds an OS advisory lock for the whole run, so a submission-triggered extractor and the regular pipeline cannot charge for the same item concurrently. A competing job defers successfully; the owner continues. Submission processing and NYCU LIFE fetching each have their own run lock. Cache updates reload and merge changed post IDs under a stable sidecar OS lock. JSON writes use unique temporary files in the destination directory, flush/fsync, and atomic replacement. Readers see complete old or new JSON; process death releases the locks. Lock files intentionally remain and must not be unlinked during operation. These protections require cooperating versions of the scripts; do not run an old extractor alongside a new one.

Accepted submissions with due extraction errors are retried even when there are no new pending reports. Exhausted/nonretryable extraction goes to manual review, deriving terminality from legacy error strings and attempt counts when newer retry fields are absent. Cooling transient errors remain accepted, and settlement never resets extraction budgets. Presence in inbox alone no longer means a report was confirmed to be a non-event. This change does not migrate terminal legacy submission statuses automatically.

No cache reset or state migration is required. This implementation performs no bulk deletion, recategorization, geocoding or avatar update. Operator recovery of exhausted records should be a deliberate, record-specific action after checking the cause; `--retry-errors` deliberately cannot flood an exhausted budget by resetting all records.

## Time contract and builder handoff

NYCU LIFE no longer uses a future activity start for `posted_at`. Its structured records and new inbox items distinguish:

- `first_seen`: stable discovery time, carried from previous structured data, seen state or existing inbox before falling back to this fetch.
- `fetched_at`: time of the current fetch (structured records update it; append-only inbox retains its original observation).
- `published_at`: a valid, timezone-bearing API `publishedAt` at or before the fetch; otherwise null.
- `publication_time_basis`: `source` when publication is known, otherwise `first_seen`.
- `posted_at`: compatibility time, known publication or stable discovery; never event start.
- `start_at` / `end_at`: activity time only.

NYCU LIFE keeps historical structured records absent from later API snapshots. An empty successful response cannot erase the archive. Existing field values not owned by the API adapter are retained when an activity is refreshed. An inbox row also prevents re-appending after a crash between the inbox write and the seen-state write.

Known pre-existing limitation: NYCU LIFE commits inbox/seen before the structured archive. If the archive save fails and the next successful API snapshot omits that activity, it can remain in inbox/seen without a structured event. Closing that older crash window needs coordinated commit/journal ordering and is outside these retry fixes. Existing committed structured history remains preserved. Atomic JSON writes fsync the temporary file, but do not fsync the parent directory; these process-death guarantees do not claim power-loss durability.

Builder integration is complete locally; deployment remains the root operator's responsibility:


1. `load_events(now=...)` validates each candidate before selecting discovery: event `first_seen` / `first_seen_at`, then extraction record `first_seen`, then legacy record `ts`; NYCU LIFE uses stable seen-state evidence after event candidates. A valid event timestamp keeps priority; malformed/future event or record values cannot mask a valid fallback. Unknown discovery stays empty, and the supplied clock is only a validation ceiling.
2. One resolver supplies feed `posted_at`, directory `updated`, org post dates and event source metadata. It normalizes offsets to Taipei and rejects invalid/future evidence. NYCU LIFE is identified by `source_id=nycu_life_api` or `raw_source=nycu-life-api`: only an explicit, timezone-bearing `published_at` proves publication. Structured publication wins over inbox publication. Legacy NYCU `posted_at=startAt` is ignored even after the start passes. Other adapters retain their `posted_at` publication contract unless explicitly marked `first_seen` or `unknown`.
3. Discovery prefers structured/event `first_seen` or `first_seen_at`, then inbox equivalents, compatibility `posted_at` explicitly marked `first_seen`, then the append-only inbox's original `fetched_at`. Mutable structured `fetched_at`, retry completion time, event start and the build clock cannot supply missing discovery. Feed discovery ordering uses this stable evidence, falling back to publication only when discovery is unknown. Existing feed limits, deduplication, late-pickup labels and UI/pagination behavior are retained.
4. Event sources and feed rows expose effective compatibility `posted_at`, `published_at` (null when unverified), `first_seen`, and `publication_time_basis` (`source`, `first_seen`, or `unknown`). Unknown compatibility/discovery times are empty strings. Source metadata is attached before event deduplication, preserving each absorbed source's own evidence; attaching inbox records cannot overwrite trustworthy structured publication. No Telegram policy was changed: delivery consumers must inspect the explicit basis to distinguish discovery from verified publication.
5. Builder and custom RSS `pubDate`, and ICS `CREATED`, share validated discovery resolution: event `first_seen` / `first_seen_at`, then attached source equivalents. Each candidate is validated before selection; malformed or future event evidence falls through to valid source evidence. Offsets normalize to Taipei; legacy naive observation dates mean Taipei. An observation equal to the consumer's clock is valid. Unknown dates are omitted; event start, publication and mutable fetch dates cannot supply RSS publication or ICS creation. ICS event `LAST-MODIFIED` uses explicit `updated_at` or creation; calendar `LAST-MODIFIED` uses the latest included event modification. Required ICS `DTSTAMP` uses creation, with a deterministic event-start fallback only when no valid discovery exists; that fallback is never exposed as publication or `CREATED`. `write_ics` passes its filtering clock through to discovery validation. Rebuild time no longer supplies these metadata fields.
6. Source evidence indexing receives each consumer's same validation clock. It validates source and primary-event publication/discovery independently before merging them, then merges duplicate post records using resolved evidence. Invalid source values fall through to valid primary-event values before inbox evidence is considered; an earlier invalid duplicate cannot hide a later valid candidate. Earlier valid source/duplicate evidence keeps priority within each evidence field; explicit publication still beats generic legacy `posted_at`, whose own record's basis controls whether it can prove publication. Event-level publication and discovery belong only to the primary post; alternate posts retain their own structured/inbox evidence. Resolution leaves raw input records unchanged until the explicit source-attachment step.

The integration does not rewrite inbox/cache history or delete activities, and does not change user corrections, geocodes, covers or avatars. It cannot recover a genuinely missing historical observation/publication time. Legacy extraction records lacking both event and record `first_seen` still rely on their only available evidence, `ts`; stability through future retries then depends on the extractor persisting `first_seen`. Build `generated_at`, relative age labels, upcoming/archive membership and explicit event edits can still change normally. `tests/test_builder_timestamps.py` covers synthetic past/future legacy NYCU starts, authoritative publication, repeated clocks and mutable fetch times, retry `first_seen`, retained source/alternate metadata, unknown dates and stable RSS/ICS output.

`tests/test_feed_discovery.py` checks builder RSS/ICS and custom RSS with temporary synthetic fixtures, including legacy NYCU source discovery, malformed/future candidate fallback, event precedence, timezone normalization, unknown evidence, rebuild stability and identical consumer clocks. Telegram policy remains unchanged and its existing delivery policy does not yet distinguish publication basis.

Timestamp masking regressions in `tests/test_builder_timestamps.py` exercise malformed/future primary-source metadata with known, unknown and absent inbox publication, including independent consumers before source attachment and repeated attachment/builds. They assert attached-source/feed publication and observation, directory updates, final org HTML, builder/custom RSS, and builder/custom/personal ICS. Duplicate records in both orders, generic legacy publication bases, alternate-post ownership, discovery aliases, event/cache/seen fallback and explicit clock boundaries are also covered. All fixtures are temporary; these checks do not run the live build or pipeline.

The offline tests use fixed clocks, mock provider responses and real competing child processes against temporary fixtures. Network can be guarded with `PYTHONPATH="$PWD/tests/ci_network_guard:$PWD/scripts:$PWD/tests"` and `python -m unittest test_extraction_retry test_pipeline_state test_fetch_nycu_life test_submission_extraction_retry test_run_pipeline test_submissions test_event_timezones test_event_categories test_llm_gateway`.

Round-two regressions additionally cover a real submission process opening the circuit during extraction, cooldown publication during image/content preparation, failed reservation/completion writes, death between reservation and provider entry, and four repeated deaths inside a synthetic provider across prompt upgrades. Round-two validation used the independent review's startup audit guard (all socket/DNS/listener operations, secret reads and real runtime-state access denied), rather than the CI guard above, which permits loopback test servers. No live provider, ingestion, push, deployment or production-state validation was performed.
