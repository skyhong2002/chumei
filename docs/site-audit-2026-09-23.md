## 問題與驗收條件

### A01：限制使用者輸入所觸發的伺服器對外請求

- `scripts/submissions.py:58` 的 `normalize_url()` 接受 `https://127.0.0.1/`、`https://10.0.0.1/` 等位址。
- `scripts/process_submissions.py:179` 的 `_http_get()` 直接請求，且 `allow_redirects=True`；後續截圖瀏覽器也沒有對目標與子資源做內網位址限制。
- 無網路 mock 確認：`fetch_generic('https://127.0.0.1/')` 會把該位址交給 requests。
- `scripts/push_server.py:32` 僅驗證 endpoint 以 HTTPS 開頭、長度、key 欄位為字串；同樣接受內網 endpoint。訂閱後會嘗試發歡迎推播。這是輸入限制缺口；實際能否到達特定內部服務，還受加密資料有效性、TLS 與網路環境影響。

**處理：**共用安全出站請求層，拒絕非公開 IP、loopback、link-local、私有網段；驗證 DNS 解析及每次重新導向，限制 port、大小、時間。截圖瀏覽器也需隔離內網。推播應採明確的可信服務範圍或同等出站防護，並加入流量限制。

**驗收：**內網 IP、IPv6 loopback、公開網址重新導向內網與 DNS 變化案例均被拒絕；合法投稿、合法 Web Push 仍可用。本次沒有向正式站投稿或探測內網。

### A02：ICS 應保留進行中的活動

- `scripts/build_site.py:2537` 使用 `start_at[:10] >= today` 篩選一般 ICS。
- `scripts/auth_server.py:1557` 的 `_feed_ics()` 以同樣邏輯產生自訂／已儲存訂閱。
- 本次找出 23 場開始日在今天之前、結束時間仍在未來的活動；全數未出現在 `feeds/all.ics` 及線上 `/feeds/custom.ics`。
- 例如「藏書印記：圖書章的生命故事」（8/10–10/11）、「清自攝影回顧展」（8/5–12/6）。網站列表有保留，訂閱卻沒有。
- 帳號／公開個人頁的 upcoming 分類也使用開始日判斷，需一併統一。`_calendar_ics()` 的「我會去」私密日曆保留全部已標記活動，不屬於這個漏資料問題。

**處理：**共用「尚未結束」判斷，處理沒有結束時間、全天活動、跨日、跨月及時區。

**驗收：**上述進行中活動在適用的 Feed 中保留到結束；一般、具名自訂、列表及帳號分類一致。

抽取提示 `scripts/extract_events.py:38` 要求 `+08:00`，卻沒有充分規範將來源當地時間轉換為同一瞬間。

| Taiwan Tech Summit 2026 | `evt_490332813616`：9/26 09:00 +08:00 | 9/26 09:00 −07:00 | 9/27 00:00 +08:00 |

同一矽友交流會還有 `evt_05a9433e4a6e`，時間已是正確的 9/26 07:00 +08:00，且使用同一報名 URL；應修正時間後判斷合併、保留所有來源。

來源：[矽友交流會主辦報名頁](https://luma.com/nycuaa-1ipo)、[Taiwan Tech Summit 主辦報名頁](https://luma.com/fum0o6xh)。本次直接讀取頁面 JSON-LD 的 `startDate`／`endDate` 與活動 timezone，並非僅依標題推測。

**驗收：**兩個案例在活動頁、日曆、ICS 與提醒都對應正確瞬間；同場交流會只有一個主要活動，舊連結可導向。

### A04：建站驗證與正式發布之間缺少隔離

`build_site.py:2556` 起直接寫入正式 `site/` 的資料、Feed 與 HTML；`run_pipeline.py:124` 附近則在 build、status 完成後才執行 validate。README 說明 Caddy 直接提供 `site/`。因此驗證失敗時，部分新檔案已經可被讀取；中途也可能讀到不同輪版本的 HTML／JSON。

**處理：**先在 staging/release 目錄完成全部產物與檢查，成功後一次切換正式版本；保留前一版回復。避免多個會寫入相同產物的工作互相覆寫。

**驗收：**故意讓生成或驗證失敗，正式站仍完整提供上一個版本；發布途中不出現半套資料。這是程式確認的風險，沒有在正式站製造失敗測試。

### A05：以資料新鮮度管理抓取服務

正式狀態快照：1,050 個排程來源中，579 正常、378 待排程、93 錯誤。這不是 471 個來源全部停機，也不代表主站沒有更新。

| 類型 | 總數 | 正常 | 待排程 | 錯誤 | 上次成功超過 7 天 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Instagram 貼文 | 328 | 143 | 117 | 68 | 121 |
| Instagram 限動 | 328 | 43 | 260 | 25 | 215 |
| Facebook | 328 | 328 | 0 | 0 | 9 |

68 個貼文錯誤為免費額度保留門檻下無可用 provider；限動 23 個為 `user_daily_exhausted`、2 個帳號找不到。限動排程有 205 個帳號目標為 168 小時；對短期可見內容，這種覆蓋率需要明確告知。狀態頁已有「Apify 共用額度節流中」說明，不應當作完全沒有監控。

**處理：**區分額度等待、帳號失效、真正抓取失敗；依可用預算訂出活躍來源的覆蓋與延遲目標。顯示最近成功時間及未達標比例，對連續逾期／零新增／快照停止更新建立告警。不要僅為減少紅字就把受限來源標正常。

**驗收：**能回答「重要社團多久內會更新、哪些來源已超時、限動實際覆蓋多少」；整輪程式執行成功與內容健康有獨立指標。

### A06：公開個人頁需要更明確的選擇

`auth_server.py:498` 的 `profile_public` 預設為 1；`_profile_html()` 向訪客顯示追蹤單位及未來「我會去」活動。登入頁主要說明是記住追蹤與參加標記，沒有同等明確地說明這些內容預設對訪客公開。

**處理：**新帳號預設私人，或在開啟個人頁前讓使用者明確選擇公開項目；「追蹤單位公開」與「參加行程公開」可分開設定。既有帳號行為變更需要有清楚通知。

**驗收：**未選擇公開的資料無法從個人頁及相關 API／頭像端點取得；登入、帳號設定與按「我會去」時的說明一致。本次沒有讀取非公開使用者資料。

### A07：實作真正的 404 與資產錯誤回應

正式站 `/missing-audit-page/`、`/event/evt_audit_missing/`、`/assets/audit-missing.js` 全部回應 **200、text/html、首頁內容**。不是單純缺少漂亮的錯誤頁，而是不存在的資源被當成成功。

**處理：**調整 Web server fallback，未知頁面回 404 並提供搜尋／回首頁；未知 JS、JSON、CSS 不應回首頁 HTML。動態路由與活動合併轉址另處理。

**驗收：**上述三種未知資源均回 404，正常帳號與 Feed 路由不受影響。

### A08：SEO 標題需要能區分不同場地

`test_title_h1_and_preview_description_are_unique_per_page` 失敗。聯電說明會有兩組同名同時場次：

- 9/30 12:10：`evt_37717d19a7db`（台達館 B05）與 `evt_90291e8ab873`（自強校區電機系館 1F）。
- 10/20 12:10：`evt_81086527cfda`（物理館 B1-019）與 `evt_b3c8914bd8bb`（資管大樓 IEC6019）。

目前 `build_site.py:2603`／`:2634` 只在同名同日加上時間，無法區別同時不同地點。這些場次不能因標題撞名直接合併。

**處理：**頁面 title、H1、預覽描述加入校區／場地或正式場次名稱；保留各自 canonical URL。

**驗收：**244 項測試全過，四個場次對使用者可辨識，沒有不當刪除或合併。

### A09：類別資料需要共用詞彙

正式資料除 11 種預期類別外，還有「社交」3 筆、「學術」1 筆、「講座」1 筆。抽取 schema 的 category 是任意字串；訂閱組合只有固定 11 類，auth 篩選把未識別類別視為 other，而 Bot 將「講座」查詢解讀為「演講」。

**處理：**在所有資料匯入／建站出口正規化，維護明確別名；前端、Bot、Feed、MCP 共用類別定義。

**驗收：**「講座」資料能被「演講」訂閱與 Bot 查到；未知分類進入可見的檢核清單。

### A10：補齊資料需有清單與品質標記

以實際結束時間判斷，本次有 457 場未來／進行中活動，其中 102 場未填 venue、104 場非 online 活動沒有 geo、90 場標為需報名卻沒有 registration_url；三類會重疊。這些缺值可能源於原公告沒有提供，不能全部視為抽取錯誤。

**處理：**按近期活動優先產生待補清單；區分「來源未提供」「尚未抽到」「定位失敗」，提供可用的來源與回報入口。不要猜測時間地點或把未知費用寫成免費。

**驗收：**重要近期活動可以定位／報名；無法補齊者有可理解的原因。追蹤地點與報名連結可用率。

### A11：降低手機下載與解析負擔

`/data/events.json` 解壓後 4,582,377 bytes；本次瀏覽器首次傳輸約 775 KB，伺服器已有壓縮。活動頁另載入約 1.06 MB 解壓後的 MapLibre。日曆與通知頁也讀全量活動；名錄約 10,836 個 DOM 節點。

**處理：**把近期與歷史索引分開、詳情按需取得；只有需要顯示地圖時載入地圖程式；名錄採分頁或漸進顯示。保留現有伺服器預先渲染的優點。

**驗收：**以冷快取、限速手機測量 LCP／INP 與下載量，設定效能預算。本次一般網路能操作，沒有把資料量直接等同於已確認的卡頓，也沒有宣稱通過 Core Web Vitals。

### A12：補完帳號資料生命週期

現有帳號具登入方式綁定、Feed 換發、公開開關，但未找到使用者刪除整個帳號的介面／路由。已有刪除訂閱與帳號合併的內部刪除 SQL，不等於提供刪除帳號功能。公開頁面只有簡短登入資料說明。

**處理：**提供完整的公開範圍、保存與刪除說明；建立刪除帳號流程，涵蓋登入 session、追蹤、參加、推播綁定、私密 Feed 及 Apify 貢獻憑證；說清楚哪些公開回報紀錄保留或去識別化。

**驗收：**刪除後舊 session／私密網址不可用，資料處理與說明一致。此為產品完整度檢查，未對法規符合性作結論。

### A13：持續整合與依賴版本仍待建置

`.github/` 只有 issue templates，沒有 workflow；`requirements.txt` 僅列套件名稱、未固定版本。現有測試有實際價值，但目前 SEO 失敗不會由 repository CI 自動攔截。這不排除機器外另有工作流程，僅表示 repository 無法重現它。

**處理：**加入乾淨環境安裝、單元／前端測試、產物驗證與必要瀏覽器 smoke test；記錄 Python／Node 版本與依賴 lock。CI 使用 fixture／隔離路徑，不能讀正式密鑰或發真實通知。

**驗收：**新 checkout 能依文件跑通；刻意引入 SEO／資料格式錯誤會阻擋發布。

### A14：備份還原與部署文件需可驗證

repository 沒有找到 auth／push 資料的定期備份與還原腳本；`state/backups/` 可見的是 9/5 的遷移前備份，不能據此證明之後沒有外部備份。launchd plist 使用本機絕對路徑，Caddy 正式設定不在這個 repository；Telegram 滴灌工作也沒有對應的 tracked plist，雖然 pipeline 程式註解提到它。

**處理：**確認實際排程，補定期 SQLite 一致性備份、推播狀態與必要密鑰的還原策略、保存期限及異地副本；以範本記錄 proxy 與所有服務，提供從新機重建步驟。

**驗收：**在隔離目錄／環境完成一次還原演練，能回復帳號與訂閱；列出可接受資料遺失時間與復原時間。先確認外部備份再決定是否新增，避免重複方案。

### A15：修正文字連結的辨識度
