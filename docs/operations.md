# 目前架構與維運入口

本頁維護目前設計與操作入口；`PLAN.md` 是歷史紀錄。功能與設定以 repository 的程式及下列專題指南為準，正式機是否已啟用某項服務需查 launchd、Caddy 與已發布產物，不能只看檔案存在。

## 開發、部署與日常操作

1. **開發／驗證**：照 [CI 指南](ci.md) 安裝 Python、Node、鎖定依賴、Chromium 與 Caddy，執行隔離檢查。這是唯一維護的環境與完整測試流程；不用提供正式憑證或搬入使用者資料。
2. **首次部署／新主機**：照 [備份與部署指南](backup-recovery.md) 恢復私密狀態、產生符合實際 checkout 路徑的 launchd／Caddy 設定。產生設定不代表已安裝；既有主機先核對已載入的 label。
3. **發布／回復**：照 [原子發布指南](atomic-publication.md) 在隔離目錄完成建站、驗證，再切換 `published/current`。程式或文案修改通常只需要離線重建；完整 pipeline 會抓取來源、呼叫模型，可能消耗額度。
4. **路由驗收**：照 [HTTP 路由指南](http-routing.md) 確認動態服務代理保留、不存在的頁面與資源回傳真正的 404。
5. **備份／還原演練**：依 [備份指南](backup-recovery.md) 驗證快照與刪除紀錄，在隔離目錄還原。每小時本機排程、金鑰保管、加密異地複本是分開的工作；不要把本機備份當成已具備主機毀損恢復能力。

不要將 `build_site.py` 直接輸出當作正式發布，也不要把整份 Caddy 範本覆蓋到包含其他網站的主機設定。發送工作須先確認狀態與支援的 dry run；建站和 CI 不應觸發真實通知。

## 資料流與保存位置

公開來源由 `fetch_*.py` 寫成 `data/feeds/inbox/*.jsonl`，抽取器將文字與海報整理成事件並保留快取。建站套用來源歸戶、去重、人工修正、共同分類及時間規則，再產生完整 API、初次瀏覽索引、歷史資料、HTML、ICS、RSS 與資料品質佇列。

`site/` 同時容納追蹤中的範本／資產與可變圖片快取。`publish_site.py` 複製到同磁碟 staging，建站、建立狀態快照並驗證；成功後切換 `published/current`，失敗保留前一版。Caddy 和動態服務讀取已發布版本。跨多個 HTTP 請求不保證同一快照，詳見發布指南。

使用者帳號、登入狀態、追蹤、私人訂閱與貢獻資料位於 `state/auth.sqlite3`；推播訂閱和發送狀態位於 `state/push/`。登入、訂閱簽章與 Apify 貢獻加密設定由受限權限的 `.env`／`.env.apify` 與程序環境變數提供，Web Push VAPID 私鑰則保存在受保護的 `state/push/`，均不屬於公開網站；程式不再讀取 Keychain，舊機部署前須先完成 [一次性遷移](credential-migration.md)。新帳號個人頁預設不公開；刪除帳號會留下最小刪除紀錄，讓舊備份還原時重套刪除，見 [個人頁隱私](profile-privacy.md) 與 [帳號刪除](account-deletion.md)。

## 服務清單

下表 label 皆以前綴 `tw.observe.chumei.` 開頭；間隔是範本設定，不代表每次成功或準時執行。睡眠、失敗與額度限制都可能增加延遲。

| Label | 執行方式 | 職責與本機介面 |
| --- | --- | --- |
| `auth` | 常駐 | 帳號、登入、投稿、貢獻、私人 feed；`127.0.0.1:8324` |
| `mcp` | 常駐 | 唯讀活動查詢；`127.0.0.1:8321` |
| `bot-line` | 常駐 | LINE webhook；`127.0.0.1:8322` |
| `bot-telegram` | 常駐 | Telegram 查詢 Bot，向外輪詢 |
| `push` | 常駐 | 瀏覽器推播訂閱 API；`127.0.0.1:8323` |
| `pipeline` | 每 3 小時 | 抓取、抽取、驗證與原子發布 |
| `submissions` | 每 15 分鐘 | 處理登入者回報的來源與活動連結 |
| `push-drip` | 每 30 分鐘 | 依偏好傳送活動與行前通知 |
| `telegram` | 每 30 分鐘 | Telegram 頻道發送；由部署產生器產生 plist |
| `backup` | 每小時 | 私密狀態備份，預設留 168 份成功快照；由部署產生器產生 plist |

Caddy 以 `deploy/chumei.caddy` 為本站範本：靜態 root 指向 `published/current`，帳號、feed、MCP、LINE、推播路由交給上述服務。啟用常駐服務不等於已啟用定時發送器；確認安裝範圍再操作。大部分日誌位於 `state/`，實際路徑以已安裝 plist 的 `StandardOutPath`／`StandardErrorPath` 為準。

## 資料延遲與尚需人工處理的部分

- **流程成功不等於全部來源新鮮。** `/status/` 與 `check_source_health.py` 分別呈現來源成功覆蓋、額度等待、抓取錯誤、逾期與快照年齡。詳見 [來源新鮮度](source-health.md)。現有 IG 基礎容量無法承諾所有帳號的限動每日完整覆蓋；本次修正沒有增加預算或解除供應商配額。
- **缺漏不能靠猜測補齊。** `/quality/` 列出優先檢查的活動及原始公告；缺地點、報名網址、精確座標或可信時間仍需來源核對。修正欄位或留下有證據的缺漏原因，下一次發布會更新佇列，見 [資料品質](data-quality.md)。
- **行事曆有自己的更新週期。** 竹梅 feed 保留尚未結束的活動，但 Google／Apple 等服務何時重新抓取由對方決定。海外時間需有可信時區；未知時區的內容保留待核對，不猜測後放進行事曆。
- **監控與復原有外部前置條件。** 健康檢查可持續非零退出；外部告警投遞、加密異地備份、憑證檔案恢復及真正替換主機的演練需另外配置與驗證。

## 功能驗收表

這是每次發布可重用的驗收方式，不是所有外部服務都已實測成功的保證。完整隔離 CI 使用合成資料；真實登入、裝置通知與第三方同步需另作端到端驗收。

| 功能 | 自動檢查／發布時觀察 | 外部或人工驗收 |
| --- | --- | --- |
| 活動、搜尋、地圖、歷史資料 | 索引與歷史集合一致；桌面／手機 smoke test、資源預算 | 確認重要活動的公告、地點與海報 |
| ICS、自訂訂閱、時間 | 進行中活動與時區測試；feed 產物驗證 | 行事曆服務實際訂閱與重新整理 |
| 登入、私人頁、刪除帳號 | 隔離 DB 測試、私人頁拒絕外部查閱、刪除與還原重套 | 各登入供應商授權與跨裝置流程 |
| 投稿、來源與品質 | 外連限制、欄位檢查、分類與品質報告驗證 | 上游內容缺漏與來源可用性查核 |
| SEO、404、文字連結 | 產物 SEO、Caddy 實際 HTTP 路由測試 | 正式網址、鍵盤操作與行動裝置閱讀 |
| Push、Telegram、LINE、MCP | API、篩選、發送邏輯測試；不發真實通知 | 授權的測試裝置／帳號與服務憑證 |
| 發布、備份、監控 | 建站失敗保留舊版；快照完整性、隔離還原、來源健康判定 | Caddy 啟用、排程存活、備份新鮮度及異地復原 |

專題參考：[共同活動分類](event-categories.md)、[瀏覽資料量](browser-performance.md)、[外連安全](outbound-security.md)。
