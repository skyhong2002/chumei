# Web Push 發送收據與重試

`scripts/publish_push.py` 的發送狀態為 `state/push/publish.json`，格式版本 2。
它先保存待送工作與收件裝置，只有推播供應商成功回覆後才保存該裝置／活動的
`sent` 收據。供應商接受請求不保證使用者已看到通知。

## 活動、摘要與提醒

- 首次正常執行只建立目前可推活動的 baseline，不發通知。新活動仍須今天或之後
  開始、未被拒絕、來源貼文不超過 14 天；01:00–08:00 保留新活動與重試至早上。
- 每場活動在首次規劃時固定符合偏好的裝置集合；帳號追蹤依當時帳號資料判斷。
  同一裝置命中超過三場會建立一份摘要工作，固定其活動成員。重試不會混入後來
  的活動，也不會重送已成功的裝置。不同摘要有各自穩定的通知 tag。
- 每份工作第一次嘗試前保存完整 payload，重試沿用其標題、時間、地點、內文、
  圖片、URL 與 tag；後來修改活動資料或合併 ID，不會重建已保存的通知內容。
  例外只有移除不再適用的摘要成員，以及提醒的「明天」／「今天」字樣。摘要
  縮減時使用首次保存的各成員標題與日期，不能帶入後來修改的內容。
- 摘要一次成功會替所有成員各存一筆裝置收據。失效、被拒絕或已移除的成員會
  取消；其餘成員仍可送出。活動合併後沿用別名的 baseline／成功收據以避免重播。
  提醒同樣檢查該帳號／裝置的所有別名收據，包含同輪較早完成的工作，避免兩份
  舊提醒合併後重送；舊格式提醒紀錄則作為該帳號所有裝置的歷史邊界。
- 沒有符合裝置的活動也保存完成紀錄，避免日後新增訂閱時重播舊活動。
- 「我會去」仍在前一天或當天提醒，固定當次帳號的裝置集合，但每個裝置各有
  收據。部分失敗只重試失敗裝置；來源貼文即使超過 14 天也仍可提醒。重試時
  重新檢查活動日期、帳號綁定及「我會去」，取消已撤回或已不適用的工作。
  「明天」跨日重試會改成「今天」。帳號 DB 讀取失敗會停止本輪，不能當成撤回。

`sent` 與 `reminders` 是保留相容性的活動索引，不代表每個索引項目已發送。
版本 2 項目的 `devices` 保存各裝置的狀態與 `delivery_id`；`deliveries`
保存實際發送工作、固定成員、帳號綁定、凍結 payload、嘗試次數與下次時間。
只有裝置狀態 `sent`
有 `sent_at`；`complete` 表示工作已處理完畢，也可能包含 `gone`、`cancelled`
或 `exhausted`，不能算成成功送達。

## 重試與失效裝置

每份工作每輪最多嘗試一次，含首次最多五次。失敗或中斷後依 30 分鐘、1 小時、
2 小時、4 小時的間隔等待後續排程；退避上限為 6 小時，程式不自行睡眠。
嘗試前先保存 `sending` 與次數，逾時／連線錯誤保存 `retry`；耗盡次數保存
`exhausted`，不標成已送。HTTP 404／410 保存 `gone` 並移除訂閱，同輪其他工作
不再嘗試該 endpoint；若移除失敗，下輪仍會嘗試清理，不再發送。

每次保存發送意圖後、呼叫 transport 前，重新讀取訂閱檔並確認裝置仍存在且帳號
綁定未改變；取消已退訂、解綁或改綁的工作，不加入新裝置。訂閱讀取失敗會
停止本輪。這個最終讀取是撤回邊界：先完成的退訂會阻止發送，讀取之後才完成的
退訂仍可能遇到已開始的請求。publisher 不持有訂閱鎖等待供應商回覆。

有 `retry`、`sending` 或 `exhausted` 工作時以非零退出，並保留舊的
`last_success_at`；`last_run_at` 記錄本輪完成時間。耗盡工作不自動重新啟動，
需維護者在授權的維運時段核對原因與可能送達情況後處理。保留成功收據，
不要刪除整份狀態來重試，否則會破壞歷史邊界。

## 保存、中斷與遷移

正常發送持有 `publish.json.lock`，重疊啟動的另一個 publisher 會直接退出。
每次狀態轉移先以原子替換與 `fsync` 寫入 `publish.json.journal`，再保存 JSON
主檔，成功後刪除 journal；檔案權限為 `0600`。主檔更新失敗時立即停止後續發送，
下輪從 journal 恢復，已保存的成功裝置不會因主檔較舊而重送。遞增的 `revision`
會避免備份中的舊 journal 覆蓋較新的主檔。損壞的 journal 會停止發送，不退回
可能缺少收據的舊主檔。

備份／還原應保留同一時間的主檔及存在的 journal；先停 publisher 可取得一致
快照。單獨還原舊主檔、刪掉 journal 或回退到不支援版本 2 的 publisher，都可能
遺失待重試進度。新程式讀取版本 1 時保留所有 `sent`／`reminders` 的歷史成員，
包含 baseline 及空的舊紀錄，作為禁止重播的邊界。舊版沒有裝置收據，無法安全
推論誰漏收，所以不自動重播任何舊紀錄。

較早的版本 2 工作可能沒有凍結 payload 或 `recipient_user_id` 帳號綁定。
尚未嘗試的活動／摘要工作會在第一次發送前，將本輪首次觀察到的帳號綁定
（含未綁定的 `null`）、內容與發送意圖一併保存；升級前的綁定無從還原。
之後跨程序重試沿用已保存的綁定，不會跟隨裝置改綁或解綁到另一個帳號。
已嘗試但沒有 payload 的工作無法還原當時的內容，改存 `exhausted` 與
`reason: missing_frozen_payload`，維持非零退出供維護者核對，不重新建構後自動重送。
即使已有 payload，已嘗試的活動／摘要工作若仍缺少帳號綁定，也無法推論原本
收件帳號，改存 `exhausted` 與 `reason: missing_recipient_binding` 供人工核對，
不以目前綁定補值或自動重送。舊提醒已保存 `user_id`，可據此補存帳號綁定，
仍檢查「我會去」及目前綁定。這些工作原有的成功收據與歷史索引都會保留。

Web Push 沒有這裡可用的冪等發送鍵。若供應商已接受，但回覆逾時，或程序在
保存成功 journal **之前**中斷／磁碟失敗，仍可能重複。這些不確定的工作會沿用
通知 tag、退避時間與五次上限；通知 tag 可替換仍顯示中的通知，不提供 exactly-once
保證。`sent` 只表示已收到供應商成功回覆並寫入收據。

狀態記錄裝置雜湊、帳號／活動 ID、通知內容與發送進度，不存 endpoint 或加密金鑰；錯誤
日誌只列例外類別，不列可能帶私人 endpoint 的供應商訊息。整個 `state/push/`
仍屬私密資料。`--dry-run` 只預覽，不寫收據、遷移、journal 或 lock，也不發通知。
